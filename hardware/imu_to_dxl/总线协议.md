# `imu_to_dxl` 总线协议 · 固件实现规格

这份是给**写固件的人**看的接口契约。板子的职责一句话：

> **在舵机总线上冒充一颗 ID 200 的舵机，主控读它就回 IMU 数据。**

主控每 tick（50 Hz）发一条 `sync_read`，一次把 ID 200 和 15 颗舵机全读回来。板子答不上，
**这一 tick 连带 15 颗舵机的数据一起丢**（一条 sync_read 是一笔事务）。

- 可执行版本：[`tools/imu200/imu200.py`](../../tools/imu200/imu200.py) —— 假小板、测试向量、验收检查，三合一
- 验收：固件写完跑 `python imu200.py check --port COMx`，它发的就是主控会发的包，判的就是主控会判的东西
- 主控侧的真实代码在 fork 的 [`duck-control/src/imu.rs`](https://github.com/UnitClaw/microduck/blob/feetech/duck-control/src/imu.rs)
  和 `bus.rs`，本文每条判据都注明了出处
- 整体方案背景见[飞特适配架构 §4](../../software/飞特适配架构.md)
- **固件实现**：[`firmware/`](firmware/) 0.2.0（2026-09-22）。主机测试 + 真协议代码上模拟总线的 `check` 验收全过，**真总线待实测**。下文标了「0.2.0 实现」的，是写固件时对原规格的细化或修正，理由写在旁边

> **标注约定**：〔手册〕= 飞特官方文档原文；〔源码〕= 主控代码里读得到的事实；
> 〔推断〕= 本文按带宽和时间预算推出来的，**需要台架实测覆盖**。

## 1. 链路

| 项 | 值 | 出处 |
|---|---|---|
| 物理层 | 单线半双工 TTL，3.3 V | 〔手册〕 |
| 波特率 | **1 Mbps**，8N1 | 〔手册〕出厂值；寄存器 6 = 0 |
| 字节时间 | 10 µs（10 bit/字节） | 推算 |
| 设备 ID | **200**（`0xC8`） | 〔源码〕`bus.rs: IMU_DXL_ID` |
| 字节序 | 小端 | 〔手册〕磁编码系列 |
| 帧格式 | `FF FF ID LEN INSTR/ERR ...params... CHK`，`LEN = 参数数 + 2`，`CHK = ~(ID+LEN+INSTR+Σparams)` | 〔手册〕`SCS通信协议` §3 |

**STS 系列没有可配置的应答延时寄存器**——地址 7 在 STS 内存表里是「预留地址」，不是 Dynamixel 的
return delay time（SMS 系列才是）。所以时序只能靠固件自己控，见 §5。

## 2. 主控会发什么

运行时**只发一条**：

```
sync_read（0x82）  地址 56，长度 15，ID 列表 [200, 20..24, 30..34, 10..14]
ff ff fe 14 82 38 0f c8 14 15 16 17 18 1e 1f 20 21 22 0a 0b 0c 0d 0e 12
```

调试台和 FD 软件还会发 `PING`、`READ`，偶尔手滑发 `WRITE`。**主控运行时从不写这块板、不给它配参数**
〔源码〕——固件把行为写死即可。

---

## 3. 15 字节块

地址 56 起 15 字节。**主控只看前 12 字节**〔源码〕`imu.rs: IMU_BLOCK_LEN = 12`，后 3 字节是为了凑成跟舵机一样的块长。

| 偏移 | 字节 | 内容 | 格式 |
|---|---|---|---|
| 0–1 | 2 | 陀螺 X | i16 小端，**17.5 mdps/LSB**（±500 dps 量程） |
| 2–3 | 2 | 陀螺 Y | 同上 |
| 4–5 | 2 | 陀螺 Z | 同上 |
| 6–7 | 2 | 四元数 x | IEEE 754 **binary16**（半精度），小端 |
| 8–9 | 2 | 四元数 y | 同上 |
| 10–11 | 2 | 四元数 z | 同上 |
| 12 | 1 | **采样计数**，每换一块新数据 +1，255→0 回绕 | u8 |
| 13 | 1 | **状态位**，见 §4 | u8 |
| 14 | 1 | 保留，**固件必须填 0** | u8 |

**四元数的 w 由主控算**（`w = √(1 − x² − y² − z²)`）〔源码〕，板子不要发 w。

### 坐标系：不要做任何变换

块里放**芯片原始轴序的裸数据**。安装方向的旋转由主控做（`DEFAULT_MOUNT` = 绕 Y +90°，
躯干 = `[+raw_z, +raw_y, −raw_x]`）〔源码〕。

> **固件不得重排轴、不得翻符号、不得做任何坐标变换。** 猜错的话鸭子会朝错误方向倒，
> 而所有电气层面的检查都会通过。板子的安装朝向必须跟原版一致；装法不同就改主控的 mount 四元数，不要改固件。

## 4. 状态字节（byte 13）

| 位 | 含义 |
|---|---|
| BIT0 | IMU 融合（SFLP）还没就绪 |
| BIT1 | 跟 IMU 芯片的通信失败（SPI/I²C 出错） |
| BIT2 | 自检失败 |
| BIT3 | 上一次被读之后，块被刷新了**超过 4 次**（≥ 5 次，说明主控读得太慢，< 约 30 Hz）。0.2.0 实现：原写「2 次以上」—— 120 Hz 采样、50 Hz 读每次本来就刷新 2~3 次，那样一半的帧都会报，没意义 |
| BIT4–7 | 保留，填 0 |

主控目前不解析这个字节，它是给人和调试工具看的。〔推断〕位定义是本文定的，固件和工具按这个来。

0.2.0 实现的映射：BIT0 = 快照没 ready 或四元数全 0；BIT1 = IMU 错误码为 SPI / 复位超时 / 配置 / 数据过期 / FIFO；BIT2 = 错误码为身份不符（WHO_AM_I ≠ 0x70）。

## 5. 时序

**没有任何飞特文档给出应答延时的数值**，手册只说「舵机返回应答包顺序按指令包中 ID 顺序返回」。
所以下表除了波特率和帧长，**其余都是按 1 Mbps 和 tick 预算推的，必须台架实测覆盖**。

| 项 | 值 | 出处 |
|---|---|---|
| 指令帧（16 个 ID 的 sync_read）= 24 字节 | **240 µs** | 推算 |
| 单个应答帧 = 21 字节 | **210 µs** | 推算 |
| 16 个设备的纯线上时间 | 240 + 16×210 = **3.6 ms** | 推算 |
| 一个 tick 的总预算 | **< 6 ms** | 〔源码〕架构文档 §5 第 4 项的验收标准 |
| ⇒ 留给 16 次总线转向的余量 | 2.4 ms ÷ 16 = **平均 ≤ 150 µs** | 推算 |
| **T_resp**：收到指令帧最后一个停止位 → 板子第一个起始位 | **标称 50 µs，抖动 < 10 µs，硬上限 100 µs** | 〔推断〕 |
| 半双工 DE 断言 | 用硬件 DE（`CR3.DEM=1`），`DEAT`/`DEDT` 建议各 16 单位（1 Mbps OVER16 下 ≈ 1 µs） | 〔推断〕，位域对 RM0444 核 |
| 软件控制 DE 时 | **必须用 TC（transmission complete）拉低，不能用 TXE** | 半双工一号坑：TXE 一置位就切方向，最后一个字节的停止位被截掉，主控侧表现为「偶尔校验错」 |
| 总线空闲判据 | USART **IDLE** 标志（1 个空闲帧 = 10 bit = 10 µs），IDLE + DMA 切包 | 〔手册〕STM32 USART |
| 残帧丢弃 | 收了一半的帧，若字节间隙 **> 500 µs** 整帧丢弃、重新找 `FF FF` | 〔推断〕不做这条，截断帧会和下一帧粘连，总线上凭空多一个包，主控整条 sync_read 错位。0.2.0 实现：原写 100 µs，放宽到 500 µs —— 帧与帧之间至少隔着主控 20 ms 的 tick，残帧照样会被丢掉，而 USB 转串口偶尔在包中间插几百微秒的空档时不至于把好帧也丢了；另外校验错会丢 1 字节重新找帧头，不靠超时也能从粘连里恢复 |

**超时不是约束。** 主控侧 rustypot 整笔 30 ms、调试台找帧头 60 ms —— 答慢到 1 ms 也不会超时，
但 tick 预算会被吃穿。规格按 6 ms 预算写，不要按超时写。

> **上板第一件事**：先量飞特舵机自己的 T_resp（往 ID 列表最前面塞一个 ID 观察），**板子取同一个数**。
> 两边节奏不一致，应答排序会飘。

### 排队规则

板子**只在自己的 ID 出现在 ID 列表里时应答，且必须答在自己的位次上**。

运行时 200 恒定在列表第一位〔源码〕`bus.rs`，所以退化成「指令帧收完等 T_resp 直接发」。
**但固件不能只实现这一种情况**——调试时会把 200 挪到中间，那时候直接发就会撞上舵机的应答。

通用实现（建议照这个写）：

```
收到 sync_read，自己的 ID 在列表下标 k：
  k == 0  → 等 T_resp 后发
  k > 0   → 发送前保持接收，看到前面第 j 个设备的应答帧（ID 在前面、长度 = 读长 + 2、第 5 字节不是指令码）
            就记「前 j+1 个答完了」，
            前 k 个都答完 → 等 T_resp 后发；
            总线静默 1 ms → 当作前面有一个设备不在线，记一个空档（不在线时不能永远不发）
  等待中出现任何别的帧（主控发了新指令）→ 这一笔作废；25 ms 还没轮到 → 放弃
```

0.2.0 实现：原写「k × 250 µs 超时兜底」，这个数不够 —— 15 字节的应答帧 21 字节 = 210 µs，加上每个设备的 T_resp 就超过 250 µs 了，排得靠后时兜底会在前面设备还在答的时候触发，直接撞包。改成按「总线静默」判断缺席。

## 6. 上电时序

| 项 | 要求 | 出处 |
|---|---|---|
| 总线处理器 | VCC 有效后 **50 ms 内**必须能应答 | 〔推断〕 |
| IMU 没就绪时 | **回全 0 四元数，绝不能沉默** | 〔源码〕板子不答 = 这一 tick 15 颗舵机数据一起丢 |
| 四元数全 0 的含义 | 主控沿用上一帧，不计入 ready | 〔源码〕`imu.rs` |
| 到 ready | 主控**累计**（不是连续）25 帧有效四元数才算 ready，50 Hz 下 ≥ 0.5 s | 〔源码〕`imu.rs: quat_samples` |

## 7. 主控怎么判一帧有效（固件必须满足）

〔源码〕`imu.rs`，逐条都要过，否则这一帧不算数：

1. 四元数三分量**不全为 0**
2. 三个分量都是**有限数**（不能是 inf / NaN）
3. **norm² = x²+y²+z² ≤ 1.02**
4. 乘 mount 共轭之后 **norm > 0.5**

> 这四条里任何一条不过，主控就当这帧没来。**工具 `imu200.py` 用的是同一套判据**，
> 所以别指望「工具过了但主控挑剔」或者反过来。

### 冻结检测：固件的两条禁令

主控 `bus.rs: StaleImuTracker` **逐字节比较前 12 字节**，连续 25 帧完全相同就报
`orientation is frozen`。由此得出两条硬约束：

1. **不许对陀螺做平滑或量化**到静置时低位不跳的程度 —— 真芯片静置时低位本来就在抖，块因此逐字节在变。
   做了平滑，鸭子一静止主控 0.5 秒就报冻结。
2. **不许靠 byte 12/13 装活** —— 采样计数和状态位在 12、13，**落在主控的 12 字节窗口之外**，
   它们变化不会让块"看起来新鲜"。

## 8. 其它指令怎么应答

| 指令 | 行为 |
|---|---|
| `SYNC_READ 0x82` 地址 56 长 15 | 按 §5 的规则应答 15 字节块 |
| `PING 0x01`（单播） | 回状态帧，ERROR = 0 |
| `PING`（广播 `0xFE`） | **不应答** 〔手册〕§4.1：总线上多个设备时不能用广播 PING |
| `READ 0x02` | 按地址回对应字节（至少支持 0–8 和 56–70） |
| `WRITE 0x03`（单播） | **回一个 ERROR=0 的状态帧，内容一概忽略**。不回的话调试台每写一次卡 60 ms |
| 任何广播指令（除 sync_read） | 不应答 〔手册〕 |
| `REBOOT 0x08` | 真重启，**不应答**，800 ms 内回来（跟舵机节奏一致）〔手册〕§4.12。注意：空片第一次烧录后如果没断电重启过，软复位会进 ST 自带 Bootloader，而它监听的 USART2 正是舵机总线 —— 烧完先断电重启一次（见《踩坑记录》） |
| `0x06` / `0x09` / `0x0A` / `0x0B`、`REG_WRITE 0x04`、`ACTION 0x05`（单播） | ACK，不动作 |
| 不认识的指令（单播） | 不应答，计入诊断的坏包计数（0.2.0 实现） |

**应答帧的 ERROR 字节恒为 `0x00`。** 调试台和 FD 会把它当舵机状态位解，非 0 会报出莫名其妙的过压/过温告警。

## 10. 测试向量

都由 [`imu200.py vectors`](../../tools/imu200/imu200.py) 生成，校验和已算好，可直接用串口助手发：

```
主控每 tick 发的完整 sync_read（16 个 ID，200 在最前）
  ff ff fe 14 82 38 0f c8 14 15 16 17 18 1e 1f 20 21 22 0a 0b 0c 0d 0e 12

只问 200（调试用）
  ff ff fe 05 82 38 0f c8 6b

PING 200
  ff ff c8 02 01 34

应答 · 融合还没出数（四元数全 0，状态 BIT0=1，计数 0）
  ff ff c8 11 00 00 00 00 00 00 00 00 00 00 00 00 00 00 01 00 25

应答 · 有数（陀螺 +1.75 / −0.875 / +0.0525 dps，四元数 z = 0.3827，计数 7）
  ff ff c8 11 00 64 00 ce ff 03 00 00 00 00 00 20 36 07 00 00 95
  数据段     64 00 ce ff 03 00 00 00 00 00 20 36 07 00 00
```

陀螺 +1.75 dps → `1.75 / 0.0175 = 100` → `64 00`；四元数 z = 0.3827 → 半精度 `0x3620` → `20 36`。

## 11. 验收

```bash
cd tools/imu200
python imu200.py demo                 # 先看假小板怎么答的（不用硬件）
python imu200.py check --port COM6    # 接上真板子，13 项逐条 PASS/FAIL
```

`check` 会验这些（全部按主控的真实判据）：

- PING 有应答、上电多久能答
- 单播 READ 能读块，保留字节是 0，END = 0
- **完整 16 个 ID 的 sync_read**：IMU 和 15 颗舵机都答、`bad_id = 0`（错位一次后面全废）、无校验错
- 采样计数每帧 +1~4（恒 0 = IMU 没出数但总线处理器还活着）
- 12 字节窗口最长连续相同 < 25 帧（冻结判据）
- 主控会接受的帧数、多久到 ready
- **事务耗时 p99 < 6 ms**（tick 预算，不是 60 ms 超时）
- 广播 PING 不应答、写寄存器不会把板子写坏

日志落在 `tools/imu200/logs/`：原始收发十六进制 + 每帧一行 JSONL（帧号、耗时、计数、陀螺原始值、
四元数位型、12 字节窗口）。「偶尔丢帧」「数据不动」这类问题靠翻这个文件定位。

还要人工确认一条工具测不了的：**板子水平静置时，解出来的重力应该 ≈ `[0, 0, −1]`**
（`imu200.py` 的 `decode_block` 会给 `gravity`）。装反 90° 的板子能通过上面每一条检查，然后鸭子往错误方向倒。
